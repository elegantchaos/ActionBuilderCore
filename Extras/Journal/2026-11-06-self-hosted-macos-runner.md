# Self-Hosted macOS Runner

- GitHub's hosted macOS runners are often slow to start, and Sam has a dedicated Mac mini runner. Generated jobs on Apple platforms now pass `runner: ${{ (!github.event.pull_request.head.repo.fork && vars.SWIFT_CI_MACOS_RUNNER) || '<hosted image>' }}` to the reusable jobs, so setting `SWIFT_CI_MACOS_RUNNER` as an organisation variable moves them to that runner. Linux jobs are unchanged.
- The generated output names no particular runner or person, so packages generated by anyone else behave as before: without the variable, every job falls back to the compiler's hosted image.
- The guard was going to compare `github.actor` with Sam's login, but that would have put his login in everyone's generated workflows. Instead it excludes pull requests from forks, which keeps untrusted code off the runner. Anyone with push access also uses it, and a second variable naming allowed actors could narrow that later.
- GitHub has no native fallback from a self-hosted to a hosted runner. A probe job that checks the runner's status through the API and then picks a label would add one, but it needs an admin-scoped token and has a small race. Sam judged it not worth the bother: while the variable is set, jobs queue if the runner is offline.
- The Xcode resolution step scans `/Applications/Xcode*.app`, so the runner's Xcodes must sit directly in `/Applications`. A nested folder such as `/Applications/Xcodes/` is not found.

## Trial on Runner-Stornoway

- With `SWIFT_CI_MACOS_RUNNER=self-hosted` set on the elegantchaos organisation, a re-run of this PR's `Tests` jobs requested `self-hosted`, so the expression works. A run queued before the variable was set kept its hosted labels: the runner is chosen when a job is queued, and unsetting the variable later doesn't redirect jobs already waiting.
- On GitHub Free, organisation variables only reach public repositories, so private repositories need repository variables. Repositories under a personal account can't use organisation runners at all.
- Stornoway was online and idle but was never offered the jobs. It's in the organisation's `Default` runner group, which most likely doesn't allow public repositories.
- Stornoway's Xcodes are all 27.x, kept in `/Applications/Xcodes/`, and the runner account can't write to `/Applications` to add symlinks. More fundamentally, it runs macOS 27, which can't run Xcode 26, so it can never serve the Swift 6.2 jobs these matrices include.
- Outcome: the variable was unset and this PR parked as a draft. A workable design would route only the jobs whose Xcode a runner actually has, perhaps with a per-Swift-version variable, and is not a single switch for every Apple job.
